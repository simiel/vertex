# Implement the Vertex Sanity content model, Studio, and server read layer

## Goal

Implement Vertex’s Sanity content model and authoring Studio for `course`, embedded `module`, `lesson`, `instructor`, and `category`, plus a server-only Sanity read client and typed data-access layer for the Next.js web app.

## Skills and guidance read

- Repository instructions in `AGENTS.md`.
- `sanity-best-practices` skill.
- `sanity-best-practices` schema reference: `references/schema.md`.
- `sanity-best-practices` Next.js integration reference: `references/nextjs.md`.
- `sanity-best-practices` project-structure reference: `references/project-structure.md`.

## Code and configuration inspected

- `sanity.config.ts`: current embedded Studio configuration with `basePath: '/studio'`, Vision, and structure tools.
- `sanity.cli.ts`: current root CLI config reading public project and dataset variables.
- `sanity/schemaTypes/index.ts`: currently empty schema registry.
- `sanity/structure.ts`: currently lists all document types.
- `sanity/lib/client.ts`: current public `next-sanity` client using CDN reads.
- `sanity/lib/live.ts`: current `defineLive` setup without the required server/browser token configuration.
- `sanity/env.ts`: public project/dataset/API version accessors.
- `app/studio/[[...tool]]/page.tsx`: legacy embedded Studio route.
- `package.json`: Next.js 16.3.2, `sanity` 5.31.2, `next-sanity` 13.3.3, and Clerk already installed.

## Decisions and assumptions

- Follow the repository architecture rule that Studio and web are separate workspaces. Create a standalone `studio/` workspace and do not extend the legacy embedded `/studio` route.
- Preserve the existing web app route structure and keep the existing embedded route untouched until the standalone Studio is verified; if removing it is necessary, document that as a separate migration decision rather than silently deleting it.
- Use Sanity document IDs generated by Sanity. Do not create deterministic IDs for ordinary content.
- Use references for reusable `instructor` and `category` documents. Keep `module` as an embedded object inside `course`, with ordered lesson references.
- Lessons do not store a parent course. Course/module relationships are resolved from the course’s ordered lesson references.
- Use Portable Text for lesson notes. Do not introduce Markdown content fields.
- Use the existing environment variable names and do not print or commit secret values. Add/update `.env.example` only with variable names and safe placeholders if needed.
- The web read layer is server-only. It must not expose a Sanity read token, write token, or private dataset access to browser code.
- Content reads should use the private dataset through a server-configured client. Public project ID/dataset values may be used for configuration, but private reads require the server token.

## Content model requirements

### Course document

- Required title and slug.
- Summary/marketing description.
- Cover image with hotspot/crop support.
- Level as a constrained list: beginner, intermediate, advanced.
- Price as a numeric display field with sensible validation.
- Optional popular flag.
- Student count display field with non-negative validation.
- Ordered learning outcomes as embedded objects, each with icon identifier, title, and description.
- Required reference to one instructor.
- Required reference to one category.
- Ordered modules array using an embedded `module` object.

### Module object

- Required title.
- Summary.
- Ordered references to lessons.
- Do not store module or lesson numbering; derive labels from array order.

### Lesson document

- Required title and slug.
- Required video URL.
- Poster/thumbnail image.
- Duration in seconds or a clearly documented numeric duration field.
- Free preview flag.
- Non-negative student count display field.
- Notes as Portable Text.
- Ordered key points.
- Optional pro tip.
- Ordered resources with constrained resource type, title, description, and URL.
- No parent-course reference.

### Instructor document

- Required name and slug.
- Photo.
- Expertise.
- Bio as Portable Text or rich text appropriate to the existing content conventions.

### Category document

- Required title and slug.
- Description.

Use `defineType`, `defineField`, and `defineArrayMember` consistently. Assign suitable Sanity document icons from `@sanity/icons` using direct subpath imports. Add field-level validation for required values, URL formats, non-negative numbers, and sensible string lengths.

## Studio requirements

- Create a standalone `studio/` package with its own `package.json`, `sanity.config.ts`, `sanity.cli.ts`, and schema source.
- Reuse or move the model definitions without duplicating competing schema sources.
- Configure the Studio with the existing project ID, dataset, API version, schema, Structure tool, and Vision tool where compatible with the installed Sanity major version.
- Organize the Desk structure into clear groups for Courses, Lessons, Instructors, Categories, and any useful divider/list presentation.
- Make the course editor practical: modules and lesson references should be easy to order and inspect.
- Configure Studio-local development at its own port, with documented commands to run it alongside Next.js.
- Keep `/studio` as-is unless a deliberate migration is required and verified; do not leave two independently edited schema implementations.

## Server-side read client and data layer

- Keep `sanity/env.ts` limited to safe configuration accessors and add a server-only secret-token accessor without exposing it to client modules.
- Add a server-only Sanity client configured for the private dataset and read token.
- Add typed query definitions and data helpers for at least:
  - all published courses for the catalog;
  - a course by slug, expanding instructor/category and ordered modules/lessons;
  - a lesson by slug, with notes, key points, pro tip, resources, and reverse course/module context;
  - instructors by slug and their related courses;
  - categories and courses grouped/filterable by category.
- Use GROQ projections that include `_key` for arrays and avoid returning unrelated fields or whole documents.
- Use `defineQuery` where supported by the installed `next-sanity` version and keep query parameters explicit.
- Use a server-only fetch helper with Next.js cache/revalidation tags appropriate for course, lesson, instructor, and category reads.
- Do not call Sanity directly from client components. Do not add write APIs or progress/auth state in this task.
- If `defineLive` is retained, configure it correctly for server and browser tokens and render `SanityLive` only where the architecture permits; otherwise keep this task’s read layer explicit and server-only.

## Security considerations

- Never read, print, or commit `.env.local` contents.
- Keep `SANITY_API_READ_TOKEN` and any write token server-only.
- Do not put tokens in `NEXT_PUBLIC_*` variables.
- Do not make the private dataset public.
- Validate route/query parameters before passing them to GROQ.
- Keep Studio authentication managed by Sanity; do not connect it to Clerk in this task.

## Expected files to touch

- Create standalone `studio/` workspace files and schema files.
- Create or update server-only files under `sanity/lib/` and `sanity/queries/` in the web app.
- Update root package scripts/documentation only as needed to run web and Studio independently.
- Update `.env.example` with safe variable names if it exists or is missing.

## Acceptance criteria

- The Studio opens locally as a standalone workspace and lists the five requested content areas.
- Authors can create/edit courses with ordered embedded modules and lesson references.
- Authors can create/edit lessons, instructors, and categories with the required fields and validations.
- Studio schema validation catches missing required fields, invalid URLs, invalid levels, and negative counts/durations.
- Web server-side helpers can fetch catalog, course detail, lesson detail, instructor, and category data using the private Sanity client.
- No Sanity secret or private token reaches browser bundles.
- No client component directly imports the server-only client or secret-token accessor.
- Existing `/` and `/design-system` routes continue to compile without unrelated visual changes.
- `npm run lint` passes without new errors.
- Web production build and Studio build/type checks are run and their real output is reported.

## Exact manual test steps

1. Start the standalone Studio from `studio/` and open its local URL.
2. Sign in with the Sanity account that has access to the linked project.
3. Create a category and instructor.
4. Create two lessons with valid URLs, notes, key points, and resources.
5. Create a course, select the category/instructor, add a module, and add the lessons in order.
6. Confirm Studio validation blocks missing title/slug/URL and negative numeric values.
7. Start the Next.js web app with the required server environment variables configured.
8. Exercise each server data helper from a server route/page or a focused test and confirm the expected projected shape.
9. Inspect the browser bundle/import graph to confirm no private Sanity token is exposed.
